# Source scan, 7 September 2026

Norway has never been in the index.

`config/factors.yaml` lists the EU/EEA country codes as a bare YAML sequence, and YAML 1.1
reads the token `NO` as boolean false. So `eu_eea_countries` contains the value `False`
where it should contain the string `'NO'`, `'NO' in eu_eea_countries` returns False, and
every Norwegian row `normalise.py` has ever seen was dropped one line into the filter.
There are 126 of them, all from azure `norwayeast`, collected daily since 2026-08-16.

```python
>>> from tci.config import load_factors
>>> 'NO' in load_factors().eu_eea_countries
False
```

That is the whole bug. It is one character of quoting, and it is not mine to fix here:
adding a country to the constituent population is a minor methodology change under
GOVERNANCE.md §1, so it needs a version bump, a CHANGELOG entry, `python -m tci.run docs`,
and one publication's notice before the first print computed under it. What I have done is
make it impossible to reintroduce. `config/regions.yaml` quotes every country code,
`load_regions()` refuses a non-string code outright rather than coercing it, and
`tests/test_sources.py` carries a strict xfail that will start failing the moment
`factors.yaml` is fixed, forcing the marker off in the same commit.

The 2026-09-06 headline printed $3.25/GPU-hr on exactly five providers, against a
`min_providers` gate of five. Nine of the eleven series gapped on `insufficient_sources`
the same day. Norway would not have moved the print much, since azure sits in the
hyperscaler segment and the headline excludes it. It would have been a sixth name in the
panel, though, and a real constituent of `-HS`, which gapped at three.

Index Futures on NYMEX on 5 October 2026**, pending regulatory review. Cash-settled
against Silicon Data's published rental indices, which are built from around 150,000 daily
verified pricing records across 50 to 100 platforms in 40 to 50 countries.

Read the GOVERNANCE.md preconditions next to that. Fifteen independent constituents, five
of them executable, 180 consecutive collection days, an oversight committee, external
assurance. This panel has five constituents and 36 collection days. The gap is not
methodology. The methodology here is better documented than most of what it competes
with. The gap is population and time, and both are what this process exists to fix.

Recorded as a `watchlist` row rather than a source. When the contract specs publish, the
methodology behind them is free peer review.

## Four candidates were already installed

The most useful thing found this month required no new dependency and no new request. The
gpuhunt collector queries three providers:

```python
PROVIDERS = ("aws", "azure", "gcp")
```

The package ships fifteen. Six more have offline catalogs, which means they are already
downloaded and queried locally, so reading them costs nothing at all. Live query,
7 September:

Oracle is the one that matters. It is a fourth hyperscaler, the panel has never carried
its name, and it reaches four shadow blocks in the same line of config. Lambda adds a
neocloud with a genuinely public rate card behind it.

The other two are more interesting than they look. `verda` and `nebius` are both currently
hand-maintained static entries in `config/providers/`, carrying a `last_verified` of
2026-07-18. That is 51 days old, past the 45-day warning, and 39 days from the 90-day
exclusion that would silently drop datacrunch out of the headline. datacrunch printed $3.25 on
2026-09-06. It *is* the median. Swapping a staleness clock for a feed on the constituent
that currently sets the headline is worth doing before the clock runs out.

Crusoe, Hot Aisle, JarvisLabs and DigitalOcean skipped cleanly asking for API keys. Under
gate 1 those are not admissible anyway.

## 1,518 rows collected, stored, and thrown away

Every gpuhunt row whose region string had no entry in `REGION_COUNTRY` was stored with
`country = NULL`, and the normaliser drops those. The largest single population is gcp
`asia-southeast1` (Singapore) at 288 observations. Also in there: Tokyo, Seoul, Mumbai,
Sydney, Montreal, São Paulo, and London three times over.

London is the one that stings. `europe-west2` and `eu-west-2` are among the deepest GPU
regions in Europe and the pipeline has been fetching their prices daily and discarding
them for want of a dictionary entry.

I widened the map to 90 regions across ten blocks. It changes no request count, since the
catalog is downloaded whole either way, and it changes no published print, because
`normalise.py` still filters on `eu_eea_countries` and only EEA countries get through.
What it does is start the clock on the shadow blocks in `config/regions.yaml`.

Three things stay deliberately unmapped, and the reasons are in the collector: GovCloud
sells to a different buyer on a different price ladder, AWS Local Zones carry a location
premium over their parent region, and the China regions are operated by separate legal
entities on separate price lists. Each would contaminate the block it landed in.

The 1,518 historic rows stay unusable. Observations are immutable and a past date cannot
be honestly re-collected. Their `raw_json` still carries the location string, so a future
shadow series could re-derive the country at read time without touching a stored row. I
have not done that; it is only worth doing if a shadow block gets close to publishable.

## A second silent filter, not fixed

`gpuhunt_.py` drops anything below eight GPUs before storage:

```python
if gpu_count < 8:
    continue  # unit is an 8-GPU node; smaller instances never match
```

That comment is a leftover from v0.2. Since v0.3.0 the node-size floor has been
`filters.min_gpu_count: 2`, measured, with the reasoning in `factors.yaml`. So the
collector is applying a stricter threshold than the methodology, before the observation
is written, on a source that cannot be re-collected. Every 2-GPU and 4-GPU hyperscaler
offer since v0.3.0 is simply gone.

Nine of `verda`'s fifteen rows clear two GPUs. I do not know how many clear eight.

Not fixed here for the same reason as Norway: it widens the constituent population, so it
is a governed change and it needs a notice. Flagged, and it should go in the same commit
as the Norway fix since they are one publication's notice between them.

## Sesterce

French, three sites, live public on-demand rates in USD on the homepage as of 7 September:
H100 $1.83, H200 $2.48, B200 $4.11 per GPU-hour.

$1.83 would be the lowest price in the EU panel by a distance. The current floor is seeweb
at $2.16 and the headline median is $3.25. One new constituent at $1.83 does not move a
weighted median much, which is rather the point of the estimator. It would set a new floor
and widen the observed constituent spread from $1.69 to $2.02, and it is a name the
sovereign sub-index should probably carry.

Their `/pricing` URL 404s; the rates live on the homepage and are marked as cached from
`cloud.sesterce.com` on a five-minute refresh. Whether that is server-rendered or
JavaScript decides static entry versus collector, and I have not checked yet.

## Rejected, with reasons that will outlive the decision

**GPU.ai price index.** A no-auth JSON API, free to cite with attribution, covering 12+
clouds. Passes gate 1 cleanly and fails gate 3 completely: it publishes fleet-wide floor
prices with no regional or country breakdown at all. A price with no location cannot enter
the EU headline or any future regional series. The recheck line names the one thing that
would change it.

**EuroHPC AI Factories.** Nineteen sites, six deploying in 2026 across Czechia, Lithuania,
the Netherlands, Poland, Romania and Spain. Access is free for SMEs and startups and
subsidised otherwise, so the rate reflects an allocation policy, not what a buyer pays.
Ingesting it would import a political number into a commercial index.

**ComputePrices.com** stays where it was: the API is Bearer-key gated, so a reader with no
key cannot reproduce a print from it, and it is an aggregator of other people's collection
decisions besides. Validation cross-check, never ingested.
